# Day-0 Kit：独立开发者与 AI Coding Agent 的项目协作方法

> 一套面向独立开发者和小型产品团队的 AI 辅助开发默认流程。它不是万能的软件工程规范，而是一个可根据项目风险、技术栈和生命周期持续演化的起点。

版本：v1.0  
更新日期：2026-08-04

---

## 这份文档解决什么问题

AI Coding Agent 显著降低了写代码的成本，却没有同比降低以下成本：

- 判断什么值得做；
- 把模糊意图变成可验收行为；
- 选择错误架构后的返工；
- 发现部分失败、权限、数据一致性和运维问题；
- 审查 Agent 生成的大量改动；
- 从一次项目中提炼可迁移经验。

因此，AI 时代的主要瓶颈通常不再是编码速度，而是：

> **规格质量、决策质量、验证能力和审查带宽。**

这份 Day-0 Kit 的目标，是在 Agent 写第一行正式代码之前，把关键约束显式化；在开发过程中，把探索、诊断、决策和实现分开；在项目结束后，把真正可迁移的经验写回下一次项目的起点。

它与仓库中的 [`templates/AGENTS.md`](../../templates/AGENTS.md) 配合使用：

- 本文解释**为什么这样协作、何时使用哪些机制**；
- `AGENTS.md` 是放进具体代码仓库、供 Agent 每次工作时读取的**执行契约模板**。

---

## 0. 使用方式

在新项目开始时：

1. 完成第 1～5 节的项目定义；
2. 在第一天跑通第 6 节的最薄端到端切片；
3. 从 `templates/AGENTS.md` 生成项目自己的 Agent 执行契约；
4. 每轮任务只选择第 8 节中的一种工作模式；
5. 按第 9～10 节要求 Agent 提交证据；
6. 阶段结束后按第 13 节进行复盘，但不要把每次事故都直接升级为全局禁令。

这不是一次性填写的表格。项目从原型进入生产、增加真实用户、接入支付或保存敏感数据时，应重新执行相关部分。

## 1. 先声明项目模式

不要只区分“玩具”和“正式产品”。更实用的是三种模式。

### 1.1 Throwaway：用完即弃

目的只是回答一个问题，例如：

- 某个 API 是否可用；
- 某种交互能否实现；
- 某个模型的输出质量是否足够；
- 某种架构是否具备基本可行性。

默认规则：

- 代码不进入主干；
- 不承诺可维护性；
- 可以不写测试和文档；
- 不接触真实用户数据；
- 结论比代码更重要。

### 1.2 Prototype：可能保留的原型

目的是验证产品和技术假设。代码可能继续演化，但尚未承诺生产质量。

默认规则：

- 核心路径应能重复演示；
- 允许局部技术债，但必须显式标记；
- 不应悄悄接入不可恢复的真实数据；
- 必须定义升级为 Production 的门槛。

### 1.3 Production：真实系统

只要存在以下任一情况，就应按 Production 对待：

- 有真实用户；
- 有真实或不可轻易恢复的数据；
- 失败会带来财务、信誉、合规或隐私损失；
- 系统将长期维护；
- 已经依赖生产域名、支付、认证或外部集成。

最昂贵的错误通常不是一开始选择了 Prototype，而是：

> **项目已经变成 Production，却从未显式发生过“升级”这一决策。**

### 模式升级门禁

从 Throwaway 或 Prototype 升级为 Production 时，暂停新增功能，至少补齐：

- 数据模型和迁移策略；
- 权限边界；
- 备份、恢复和回滚；
- 核心路径测试；
- 错误日志和最低可观测性；
- 依赖、密钥和环境管理；
- 生产部署流程；
- 明确的人工闸门。

## 2. Day-0 必须由人做出的四类决定

Agent 可以帮助分析，但不应在没有授权时替你决定这些问题。

## 2.1 产品契约：为什么存在

至少写清以下内容：

- **一句话核心循环**：用户做什么、得到什么价值、为什么回来；
- **目标用户**：谁在什么场景使用；
- **被替代方案**：现在用户如何解决；
- **MVP 边界**：第一个可验证版本必须具备什么；
- **三条反目标**：明确不做什么；
- **新功能筛选规则**：无法加强核心循环的想法默认进入 deferred backlog，而不是立即实现。

反目标的作用不是压制创意，而是给 Agent 一个拒绝范围扩张的依据。没有反目标，Agent 对每个新想法的默认行为往往是继续实现。

## 2.2 风险契约：失败的代价是什么

明确项目涉及哪些风险面：

- 数据是否可重新生成；
- 是否包含身份、财务、健康或其他敏感信息；
- 是否存在不可逆删除；
- 是否接入付费 API 或可能失控的计算资源；
- 是否有支付、邮件、通知等外部副作用；
- 是否需要多用户隔离；
- 是否存在合规、地区或数据驻留要求；
- 可接受的停机和数据丢失范围。

风险决定验证强度。不是所有项目都需要同样的工程门禁。

## 2.3 运行契约：系统最终在哪里运行

至少声明：

- 部署平台、账号和区域；
- 数据库和文件存储；
- 认证方案；
- 域名和回调地址；
- 运行时限制；
- 成本上限；
- 依赖引入政策；
- 密钥管理方式；
- staging 或 preview 环境策略。

这些信息通常无法从产品描述中推导出来。Agent 若不知道，往往会自行选择一个“常见方案”，而常见方案未必符合你的真实约束。

## 2.4 权威来源：发生冲突时听谁的

项目至少应区分：

- 产品意图；
- 已批准的规格；
- 架构决策；
- 当前实现；
- 运维程序；
- 任务状态；
- 历史材料。

聊天记录、TODO、roadmap 和 Agent 的建议可以提供上下文，但不应自动构成实施授权。

仓库级的推荐权威顺序和文档结构见 [`templates/AGENTS.md`](../../templates/AGENTS.md)。

## 3. 先区分可逆决策和高代价决策

不是所有问题都值得在 Day 0 进行同样深度的讨论。

### Two-way door：容易撤销

例如：

- 页面布局细节；
- 小型内部工具；
- 可替换的 UI 组件；
- 不影响外部契约的局部实现。

处理方式：快速选择、快速验证，不要过度设计。

### One-way door：反悔成本高

常见例子：

- 主数据库和核心数据模型；
- 身份认证和多租户边界；
- 对外 API 或数据格式；
- 计费系统；
- 数据区域；
- 核心编辑器文档格式；
- 会产生长期迁移成本的基础设施。

处理方式：

1. 写清假设；
2. 比较至少两个可行方案；
3. 做最小 spike；
4. 记录为什么选择；
5. 定义什么信号出现时需要重新评估。

目标不是消灭错误，而是把深入思考集中在真正难以撤销的地方。

## 4. 技术栈选择：降低胶水税，而不是追求“最现代”

AI 时代新增了一个真实的选型维度：Agent 对该技术栈是否能够稳定地产生正确实现。

但“训练语料多”不应成为唯一原则。更可靠的评价顺序是：

1. 是否满足产品和风险要求；
2. 官方文档是否完整、接口是否稳定；
3. 是否有活跃维护和真实生产案例；
4. 你是否能够理解和维护；
5. 部署、调试和迁移是否可控；
6. Agent 能否基于官方资料和实际执行验证结论；
7. 长期成本是否合理。

### 推荐验证方法

对候选技术栈做一个小型 spike，而不是只听 Agent 解释：

- 跑通最关键的边界场景；
- 要求 Agent 引用官方文档说明限制；
- 验证本地与目标环境是否一致；
- 记录失败时的调试路径；
- 检查 Agent 是否能生成正确测试和最小复现。

流行技术也可能被 Agent 自信地答错；小众技术也可能因官方文档优秀而容易协作。真正应优化的是：

> **可验证性、生态稳定性和维护成本。**

每增加一个适配层、自定义构建步骤或非标准运行时，都应说明它解决了什么不可替代的问题。把创新预算尽量留给产品本身，而不是胶水层。

## 5. 进入实现模式前：Definition of Ready

一个任务在满足以下条件前，不应进入正式实现模式：

- 可以用一句话描述目标行为；
- 至少有一个可观察的验收标准；
- 已明确可修改范围；
- 已明确不可修改范围；
- 关键产品决策没有未决分支；
- 所需环境、账号、数据和依赖可获得；
- 已列出关键假设；
- 已说明失败、停止或回滚方式；
- 已判断它是探索、诊断、规格、视觉决策还是实现任务。

一个“好点子”还不是可实现任务。一个没有可观察验收标准的需求仍然处于探索或规格阶段。

## 6. 第一天验证最薄端到端切片

不要等产品功能全部完成后才第一次部署。

第一天应尽早跑通一条**最薄的 vertical slice**，验证真实交付路径：

```text
本地代码
→ 构建
→ 目标运行时
→ 环境变量
→ 认证（如有）
→ 数据库或存储（如有）
→ 域名与回调（如有）
→ 真实请求
→ 日志与错误可见性
```

具体切片应按风险选择：

- 纯静态工具：部署一个真实页面并验证构建；
- 有数据库：写入并读回一条测试数据；
- 有认证：完成一次真实登录和回调；
- 有第三方 API：完成一次最小调用并记录成本与失败表现；
- 有后台任务：提交、执行并观察一次任务；
- 有文件：上传、读取和删除一份测试文件。

只返回 `ok` 的路由能验证部署，但不能自动证明数据库、认证和外部集成可行。切片应覆盖项目最危险、最难替换的运行约束，同时保持足够薄。

此后每次增量都应维持这条路径可运行。

## 7. 从用户动作推导可靠性不变量

对产品中每一个“用户做了一件事”的动作，至少问以下七个问题。

### 七个动作级问题

1. 用户重复触发两次，会发生什么？
2. 请求已经发出，但响应因断网、超时或切换页面没有回来，会发生什么？
3. 这个操作写了几处数据？第一处成功、第二处失败时，系统处于什么状态？
4. 两个响应乱序返回会怎样？旧响应会不会覆盖新状态？
5. 用户输入到一半刷新或关闭页面，会丢失什么？
6. 收到超长、类型错误、缺字段或恶意构造的数据时，会发生什么？
7. 操作能否撤销？不可逆操作被误触时如何恢复？

这些问题主要覆盖重复、部分失败、乱序、输入边界和可恢复性。让 Agent 的回答落成项目不变量，并尽可能通过以下方式执行：

- 数据库约束；
- 事务；
- 幂等键；
- 类型和 schema 校验；
- 回归测试；
- 状态机；
- 权限检查；
- 人工闸门。

### 七问不是完整系统设计

还应按项目风险补充以下系统级问题。

#### 身份与权限

- 谁可以执行这个动作？
- 用户能否通过修改 URL 或请求参数访问别人的数据？
- 管理员、普通用户和未登录用户的权限边界是什么？
- 服务端是否重新验证权限，而不是信任客户端？

#### 数据生命周期

- 如何备份、恢复、导出和删除？
- schema 迁移失败时怎么办？
- 数据保留多久？
- 哪些数据是权威来源，哪些只是缓存或派生物？

#### 可观测性

- 失败后如何被发现？
- 日志是否有请求 ID、用户 ID 或任务 ID 等关联信息？
- 哪些失败需要告警？
- 如何判断新部署破坏了核心路径？

#### 成本与滥用

- 输入和调用频率的上限是什么？
- AI、邮件、存储和计算的单次成本是多少？
- 重试或恶意请求是否可能造成无限账单？
- 后台任务是否可能重复产生副作用？

#### 时间与异步

- 使用客户端时间还是服务端时间？
- 时区如何处理？
- 定时任务漏跑或重复执行怎么办？
- 队列重试是否幂等？

七问是最低动作级检查，而不是安全、运维和系统设计的全部。

## 8. 每轮只选择一种工作模式

返工经常来自同一条 prompt 同时要求 Agent“想清楚”和“做出来”。一个尚未决定的方案会被完整实现，然后因为产品判断改变而整体推翻。

### A. 规格模式：决定做什么

适用于需求、架构或行为尚未确定时。

```text
只讨论，不改代码。

围绕 <问题> 给出 2～3 个可行方案。每个方案说明：
- 假设；
- 用户可观察行为；
- 失败表现；
- 放弃了什么；
- 反悔成本；
- 验证方式。

给出推荐和理由，列出仍需由我决定的问题，然后停止。
```

### B. 诊断模式：先建立因果链

适用于 bug、性能问题、环境差异和间歇性故障。

```text
不要修复代码，先复现并定位 <问题>。

输出：
1. 最小复现步骤；
2. 实际行为与预期行为；
3. 最可能的原因；
4. 区分这些原因所需的证据；
5. 最小诊断实验；
6. 已排除的原因。

证据不足前，不要修改正式实现。
```

### C. 实现模式：实现已决定的行为

```text
实现 <一句话目标>。

验收标准：
- <可观察行为 1>
- <可观察行为 2>

可修改范围：<范围>
不可修改范围：<范围>

先复述计划、假设和拟修改文件。实施后提供真实验证输出、未验证项和回滚方式。
```

是否要求“先等确认再编码”，取决于工具交互方式和任务风险。高代价或架构性任务应设置确认门；小型、可逆且规格明确的任务可以直接执行。

### D. 勘探模式：用代码回答一个问题

```text
这是用完即弃的探索，目的是回答 <问题>。

在 <分支或目录> 中实验。代码不进入主干，不要求生产质量。
最终输出：结论、证据、限制，以及是否值得进入正式规格阶段。
```

### E. 视觉与交互决策模式：低成本并行比较

```text
不要修改正式应用代码。

使用真实文案和真实数据形态，产出 3 个独立静态方案。
每个方案说明：
- 它强调什么；
- 它牺牲什么；
- 它在赌什么用户行为。

待我选择后，再进入实现模式。
```

### 不要混用模式

以下信号意味着应停止并切换模式：

- 讨论中出现“先写一版再说”，但关键产品决策仍未确定：回到规格模式；
- bug 修复没有稳定复现：切换诊断模式；
- 实现过程中发现要改变核心数据模型或外部契约：停止并进入规格模式；
- 静态原型都无法决定方向：不要在正式代码里继续高成本试错。

## 9. 每轮任务包

不要只给 Agent 一句功能描述。一个可执行任务包通常包含：

```markdown
## 目标
<一句话描述用户或系统行为>

## 背景
<为什么现在做，以及相关上下文>

## 必须阅读
- <文件或文档>

## 可修改范围
- <目录、模块或行为>

## 不可修改范围
- <明确排除项>

## 验收标准
- <可观察结果>

## 风险与不变量
- <权限、数据、幂等、兼容性等>

## 验证
- <测试、构建、手动操作或部署验证>

## 停止条件
- <何时不得继续猜测或扩大范围>

## 回滚
- <如何撤销、禁用或恢复>
```

任务大小的判断标准不是一个绝对行数，而是：

> **一个清晰意图、可独立验证、可安全回滚、你能在一次审查中理解。**

“约 400 行 diff 或 10 个文件”可以作为软警戒线，而不是硬规则。超过时，Agent 应解释为什么它仍是一个原子改动，并给出拆分方案。初始脚手架、生成文件和机械迁移应单独看待。

## 10. 验收：行为证据与实现边界都要审

Agent 的“完成”声明不是证据。

### 先看行为证据

要求提供：

- 实际运行的命令；
- 真实输出；
- 测试从失败到通过的证据；
- 手动验证步骤；
- 目标环境中的实际结果；
- 无法验证的部分及原因。

Bug 修复应优先从失败回归测试开始。无法稳定自动化时，至少建立其他可重复证据，例如：

- 最小复现步骤；
- 诊断脚本；
- 日志查询；
- 浏览器或设备矩阵；
- 截图或录屏；
- 明确的生产事件证据。

不要为了遵守“必须有测试”而写一个没有真正覆盖故障的测试。

### 再看高风险 diff

行为证据通过后，仍需检查实现边界，特别关注：

- 是否扩大了任务范围；
- 是否新增不必要依赖；
- 是否吞掉错误或弱化校验；
- 是否删除或修改了关键测试；
- 是否硬编码使测试通过；
- 是否改变权限、数据模型、外部契约或配置；
- 是否引入无法回滚的副作用；
- 是否留下新旧实现并存。

因此更准确的原则不是“只读证据，不读 diff”，而是：

> **证据证明行为，diff 证明实现边界。先审证据，再把审查带宽集中到高风险改动。**

### 人工体验仍不可省略

自动检查通过不等于产品体验可接受。关键路径至少由人完整走一次，尤其是：

- 首次使用；
- 登录与权限；
- 创建、编辑和删除；
- 错误状态；
- 移动端或关键设备；
- 支付、邮件、通知等外部副作用。

---

## 11. 停止、重置和升级条件

Agent 的边际编码成本很低，因此人容易允许它连续打补丁。应提前定义停止条件。

### 连续失败时看“信息增益”，不只数次数

不要机械地规定“三次修不好就一定是架构错误”。更实用的规则是：

> 同一问题连续若干轮没有产生新的可验证信息，就停止修改，回到诊断或规格模式。

如果每轮实验都排除了一个原因，继续诊断可能合理；如果只是在不同文件中重复猜测，应立即停止。

### 以下情况必须暂停实现

- 需要改变产品契约；
- 需要改变核心数据模型或权限边界；
- 发现任务的验收标准无法判断；
- 需要执行不可逆或生产影响操作；
- 修改范围明显超出原授权；
- Agent 开始重复已经被否决的假设；
- 会话过长，关键约束丢失或自相矛盾；
- 测试通过但真实行为仍不正确；
- 局部修复不断增加特殊分支。

### 新会话不是失败

当上下文发生衰减时，新建会话，只带入：

- 项目执行契约；
- 当前任务包；
- 已确认事实；
- 已排除方案；
- 当前分支和提交；
- 待验证问题。

不要把整段旧对话无差别复制进去。上下文越多，不等于有效约束越清晰。

---

## 12. 把 Agent 的执行转成你的知识

Agent 可以完成工作，但如果你只接受结果，能力不会积累。

对关键实现追加以下追问：

```text
解释为什么采用这个实现。
如果不这样做，会在哪个具体场景失败？
给出一个我可以自己复现的失败场景。
说明是哪条系统不变量要求这样实现。
```

要求解释锚定到当前代码和真实故障，而不是泛泛讲概念。

更进一步，可以要求 Agent 提供：

- 一个最小失败测试；
- 一个反例；
- 一个替代方案及放弃理由；
- 该知识适用与不适用的条件。

这比脱离上下文地阅读大量文档更容易形成可迁移的工程心智模型，但仍应对高风险结论核对官方资料和实际运行结果。

---

## 13. 让复盘形成闭环，但不要制造规则堆积

推荐闭环：

```text
项目契约
→ 分模式协作
→ 小范围实现
→ 证据验收
→ 工程复盘
→ 更新约束、测试或工具
```

复盘后，不要把每个事故都直接写成新的跨项目禁令。先问：

1. 这是系统性问题还是一次性事件？
2. 它适用于所有项目，还是只在某些条件下成立？
3. 最好的防护是文档规则，还是测试、类型、数据库约束、脚本或自动化？
4. 新规则会不会与已有规则冲突？
5. 它是否值得增加所有未来 Agent 的上下文负担？

### 经验成熟度

```text
Observation
→ Project-specific rule
→ Repeated pattern
→ Cross-project default
```

- **Observation**：本次发生了什么；
- **Project-specific rule**：只写回当前项目；
- **Repeated pattern**：在多个项目或多次事件中重复；
- **Cross-project default**：才进入通用 Day-0 Kit。

强因果、低成本、高收益的防护可以更快升级；依赖特定框架、团队和业务条件的经验应保留条件标签。

### 优先把经验变成可执行约束

防护强度通常如下：

```text
口头提醒
< 文档规则
< 检查清单
< 自动测试或静态检查
< 类型、schema 或数据库约束
< 权限和平台级硬边界
```

能由系统强制的，不要长期依赖 Agent 每次“记得”。

## 14. 文档和命名原则

### 记录设计意图，不复制可生成事实

Agent 可以从代码中读出当前实现，却不一定知道：

- 为什么这样设计；
- 哪些边界不可突破；
- 哪些方案已经被否决；
- 哪些代码只是临时过渡；
- 什么条件下需要重新评估。

因此文档应记录：

- 产品契约和不变量；
- 关键架构边界；
- 决策及其理由；
- 验收条件；
- 运维和恢复程序。

不要手工复制能够从 package、schema、代码或配置稳定生成的事实。

### 使用轻量决策日志

不是每个决定都需要正式 ADR：

- 小型可逆决定：commit message；
- 中型设计决定：decision log；
- 高代价架构决定：ADR。

至少记录：选择、理由、替代方案、关键假设、重新评估信号。

### 使用稳定领域命名

不要把易变的营销品牌名深度嵌入数据库、服务名和基础设施，也不要为了“中性”而使用难以理解的随机代号。

优先使用稳定领域概念，例如：

```text
note
workspace
source
capture
summary
```

目标是让代码语言与业务概念一致，同时隔离可能变化的品牌文案。

### 不变量的锚点应稳定

避免依赖易漂移的行号。优先锚定：

- symbol；
- module；
- test name；
- migration name；
- database constraint；
- ADR。

例如：

```markdown
- 创建笔记必须幂等。
  - Enforcement: `createNote()` + `client_request_id` unique constraint
  - Verification: `create-note-idempotency.test.ts`
```

## 15. 常见误区

### 误区一：把 Agent 产出速度当成项目速度

Agent 可以快速生成代码，但产品判断、验证、真实用户反馈和高代价决策不能按相同比例压缩。

### 误区二：一个超级 prompt 可以替代迭代协议

高质量初始 prompt 很重要，但真正决定结果的是：

- 每轮模式是否清楚；
- 任务是否可验收；
- 修改范围是否受控；
- 是否有停止条件；
- 是否要求真实证据。

### 误区三：所有变化都是返工

健康的原型演化、删除复杂实现、引入更清晰模型，都可能是正确进步。复盘应区分：

- 错误实现后的返工；
- 通过实验获得知识；
- 正常架构演化；
- 问题本身固有的复杂性。

### 误区四：测试通过就完成

测试可能不完整、写错或只覆盖实现细节。还需要真实行为、目标环境和人工体验证据。

### 误区五：规则越多越安全

过长、冲突和缺乏优先级的规则会降低 Agent 对关键约束的注意力。规则必须有适用条件，并定期删除失效项。

### 误区六：主流技术栈必然正确

主流栈通常降低协作和招聘成本，但不能替代产品、合规、性能和运行约束。应通过 spike 和真实部署验证。

## 17. 推荐的最小工作流

```text
声明项目模式
→ 写产品、风险和运行契约
→ 区分可逆与高代价决策

→ 让任务满足 Definition of Ready
→ 选择单一工作模式
→ 小范围实施
→ 行为证据 + 高风险 diff + 人工体验验收

→ 阶段复盘
→ 将成熟经验写回规则、测试或工具
```

## 结语

AI Agent 最擅长的是在明确边界内快速执行；最危险的是在边界缺失时，替用户补全本应由人承担的产品和架构判断。

高水平的人机协作不是寻找一句完美 prompt，而是建立一套可重复协议：

- 在动手前澄清不可替代的决定；
- 把探索、诊断、规格和实现分开；
- 控制每轮修改的意图和范围；
- 用真实证据而非自信声明验收；
- 在没有信息增益时停止打补丁；
- 把经验升级为可执行约束，而不是无限增长的提醒清单。

这套方法的最终目标不是让 Agent 写出更多代码，而是让每一轮代码更接近真实意图，并让下一个项目从更高的起点开始。
